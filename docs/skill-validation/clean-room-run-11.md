# Clean-room validation, run 11 — the first run on the shipped harness

The first run after the harness moved from prose into code
([run 10](clean-room-run-10.md) is why). Same conditions as
[runs 1–10](README.md): fresh agent, empty directory, barred from this
repository, every earlier test directory and the preserved results, allowed
only the skill directory — now SKILL.md *and* `harness/` — one prompt, no human
input. DataStream pinned; the prompt asked for the 2→4 step ratio with its
spread as the headline, and said no one-unit case was needed.

**Model: Claude Opus 5.**

## The table

Build `6ee9600b17e9ba41`, 200M-trade backlog, 10 s checkpoints, three passes
alternating asc/desc/asc, generated by the harness into `suite.md` and pasted
([raw results](run-11/)):

| cores | p1-asc | p2-desc | p3-asc | mean | spread | % of cap | src idle |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 2 | *refused* | 376,886 | 392,293 | 384,590 | 4.0% | 99.9% | 11.8% |
| 4 | 687,827 | 693,104 | 775,611 | 718,847 | 12.2% | 97.7% | 9.2% |

**2→4 = 1.869×**, range 1.75–2.06× across passes, order effect 0.96 / 0.95.
Both cases reportable under the 20% ceiling. The pipeline: block trades
allocated across exactly 3 accounts, positions by symbol (64 keys) and by
account (512 keys), 4 outputs per input, exactly-once checkpointing with an
at-least-once idempotent sink.

The refusal was the harness doing what it was built to do: 2-core pass one
read 96.4% of cap against a 98% floor, the case was marked, the suite went on,
and two passes remained to report from. The agent's explanation — its own
`df`/`docker exec` polling on the host during the window — is labelled in its
report as a hypothesis it did not test. Correct.

The measurement is 23 minutes — the same 23 the harness took driven by hand
against run 10's pipeline. The gates ran twice because the agent changed its
record format after the first pass (JSON positions at 607 B per input trade
would have written ~75 GB against 103 GB free; a delimited line is 235 B), and
the harness correctly demanded completeness and the tiny proof again for the
new build. No build-A number is in the table. The 1.5 h criterion was missed
on process, not measurement: without the rebuild and the optional ceiling it
is 1.3 h.

## What it got right, unprompted

- **Ceiling named by measurement.** Worker held at 4 cores, broker starved in
  steps: 2.5 → 1.25 cores barely moved throughput; at 0.6 the broker pinned at
  88% of its cap, the worker fell to 91.7%, and the harness refused the case.
  The refusal is the result.
- **Two of its own wrong numbers caught before use** — a fill rate misread by
  7× and a bytes-per-record figure off by 2× — and a wrong note in its phase
  log corrected in place with the arithmetic that killed it.
- **No dashboard**, with the reason written down: the harness owns the compose
  file and §6 forbids a host-side watcher, so it rendered the figure from
  `suite.json` and found three layout defects by looking.

## The one it broke — and it was prose

Two host-side watcher shells outlived `down`. Their `pgrep -f "prove.py
suite"` pattern matched their own command lines, so each waited on itself.
The harness's survival assertion cannot see a process it did not start, which
§6 says in words; the agent broke the rule in words and caught it with an
independent re-assert. Runs 1–11, without exception: rules written as guards
are obeyed, rules written as prose are broken.

## Noted, not explained

- This pipeline's source ran **9–12% idle** on every row, under the 15%
  ceiling; the hand-driven run on run 10's pipeline ran 0.0%. Different
  pipeline, different fan-out (4 vs 8): not comparable, and no cause offered.
- The 4-core case read 688k, 693k, 776k across the suite — and **801k** ten
  minutes later as the first ceiling step, same config. Run 10 saw its third
  passes fall; this run saw them rise. Whatever moves a case by 12–16% at a
  constant cap is unmeasured, and it is the next experiment: one case, six
  passes, nothing changed.

## What it sent back into the skill
