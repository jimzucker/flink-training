The table below is stamped `quickLook: true`, `publishable: false` in

## What the pipeline is

Hand-written DataStream operators, no SQL and no Table API:

```
kafka-source -> parse -> +- keyBy(symbol)  -> running position per symbol  -> positions-by-symbol
                         |
                         +- allocate (1 block trade -> 4 account allocations, 40/30/20/10,
                            the last account taking the remainder)
                                 -> keyBy(account) -> running position per account
                                 -> positions-by-account
```

Three job-graph vertices, two HASH edges, read off the running plan and asserted
identical on every case by the harness. 32,768 symbols and 16,384 accounts. The key
counts are large deliberately: a few hundred keys hash unevenly enough across 128 key
groups to hold the largest case below its CPU cap, and in a table that is
indistinguishable from a real scaling shortfall.

## Correctness, which the throughput is gated on

Completeness ran on a 12,000,000-trade backlog, twice, with no tolerances, for this exact
build hash:

| arm | result |
|---|---|
| clean drain | 12,000,000 symbol records and 48,000,000 account records read back; 32,768 symbols and 16,384 accounts match the manifest **exactly**; both paths net 89,154,400 |
| task manager killed at 35% of the drain | 12,095,573 and 48,376,063 records read back — **95,573 replayed records** — and every position still matches the manifest exactly; both paths net 89,154,400 |

That second row is the guarantee doing what it was configured to do: the sink is
at-least-once, so a worker failure re-emits records, and because each record carries the
*absolute* position for its key rather than a delta, the replay is harmless. The expected
answer comes from the generator's manifest, computed from the input sequence by its own
implementation of the allocation rule — never from the pipeline.

| when | refusal | what it was |
|---|---|---|
| suite, 1-core sentinel pass | "task manager used 94.5% of its 1-core cap (floor 95%) — it is not the constraint" | A **case-scope** refusal, so it marked that pass and the suite continued — which is why the 1-core case still reports on its two accepted passes. The cost is that the sentinel's first-to-last drift check is unavailable for this run. |
| calibration, three tiny proofs | "the broker hit its memory limit N times inside the window … give the broker container more memory" (2,964 and 10,648 hits, then 1,136, then 995) | Fixed before the chain — see below. Zero hits in all seven suite passes. |

Nothing else was refused inside the accepted chain. Every suite pass had six or seven
commit boundaries in its window, a 90 s warm-up to a flat trend, at least 263 s of backlog
headroom at close, and the two vantage points (committed source offsets vs. sink growth
÷ 5) agreed to within 0.57%.

## The one thing I explained, and how

The broker memory guard refused three tiny proofs. The first explanation — "the broker is
short of page cache" — predicted that 750 MiB more headroom would fix it. It moved the
count from 1,136 to 995. The explanation was wrong, and the measurement said so before it
reached a document.

What the counters said instead: the case that hit the limit was the **small** one. The
4-core case, moving four times the bytes through the same broker, hit it zero times. The
mechanism that fits every observation is that at one core the rest of the VM is idle, so
the kernel lets the broker's page cache grow until it meets the broker's *own cgroup
limit*; at four cores the worker's heap takes that memory first, global pressure keeps the
broker's cache below its cgroup limit, and the counter never fires. Prediction: raise the
limit above anything a 7.8 GiB VM can ever hand the broker and the hits go to zero.
Tested — one rig, one build, one 120M-record backlog, one variable changed, both arms
measured:

| broker cgroup limit | limit hits in window | refaults | 1-core rate | worker |
|---:|---:|---:|---:|---:|
| 3,840 MiB | 995 | 36,448 | (refused) | 100.0% of cap |
| 6,144 MiB | **0** | 29,689 | 170,642 rec/s | 100.0% of cap |

A second one-variable comparison, on the worker's fixed memory base (the term covering
metaspace, JVM overhead and the network buffer floor, which does not scale with cores).
Per-subtask memory stayed at 448 MiB in every case:

| worker fixed base | 1-core rate | 1-core GC | 4-core rate | 4-core GC |
|---:|---:|---:|---:|---:|
| 768 MiB | 170,642 | 45.8% | 615,011–618,936 | 11.2% |
| 1,216 MiB | **200,456** | **31.3%** | **675,406** | **9.3%** |

Two other build changes were made in the same window and are **not** separately
attributed: lz4 compression on the input backlog and both sinks, and writing decimal
digits straight into a byte array instead of via `String`. Both were made to cut bytes
through the broker and garbage in the worker, and both plainly did, but I ran no
controlled arm for either, so I claim no number for them.

## What I did not explain

- **Why 2→4 (1.86×) falls further short of linear than 1→2 (1.96×).** I have not measured
  a cause and will not invent one. What this run's own evidence rules out: it is not the
  broker (0.29 of its 2.5 cores at the 4-core case, source idle 0.0%, zero broker
  memory-limit hits); not the input split (8 partitions, 2 per subtask at 4 cores); not a
  different job graph (three vertices, two HASH edges, asserted identical on every case);
  not the order of the cases (descending ÷ ascending within 3%); and not the worker
  falling off its cap (98.1% mean at 4 cores). GC falls monotonically with cores here —
  26.4% → 13.7% → 8.5% — so if anything the *baseline* carries the most overhead, which
  flatters both step ratios rather than depressing 2→4. Beyond that: I do not know yet.
- **Why the 1-core case still spends 26% of its only core in garbage collection.** It was
  46% before the memory base was raised and 26% after. It is a real cost of running a
  fan-out-of-five Kafka pipeline in a ~1.7 GiB worker process, but I have not measured
  which allocation site dominates.
- **Why the 1-core sentinel landed at 94.5% of cap** when the two accepted 1-core passes
  read 99.5% and 99.6% at essentially the same throughput. One pass, no controlled arm.
- **Where this stops.** I did not run `prove.py ceiling`, so I cannot say at what core
  count the broker becomes the constraint. What the table does show is that at 4 cores it
  is nowhere near it: 0.29 of 2.5 broker cores, and the source never waited on input.
- **No dashboard was built.** §7 of the skill wants one to explain the numbers; the user
  asked for a fast look and every number here is generated from `results/`. A stated
  omission, not an oversight.

## Scope

This is one pipeline on one laptop. It supports at most "this pipeline's throughput grew
with the cores given to one worker on this rig" — and even that is not established here,
because a quick look is not a result. It says nothing about Flink in general, nothing
about a cluster, and nothing about a second worker: the axis measured is *one worker
growing*, not *workers multiplying*.
