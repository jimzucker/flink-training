# Block-trade allocation and running positions — how far it scales

**Headline: 2 → 4 cores returned 1.76× (88% of linear), and does not meet the 95%-of-linear
claim. 1 → 2 returned 2.35×. Every case was measured with the worker as the constraint,
nothing was lost, and the table is a `--quick` table — two passes per case — so it is not
publishable as a result.**

| field | value |
|---|---|
| axis | one worker growing: one task manager container capped at N cores, parallelism N, N slots |
| API level | Flink DataStream API, hand-written operators (no SQL, no Table API) |
| guarantee | state: **exactly-once checkpointing**; sink: **at-least-once**, idempotent by emitting the absolute position per key |
| checkpoint interval | 10 000 ms |
| build hash | `ffc01f5c36588ad1` (completeness passed for `ffc01f5c36588ad1`) |
| passes per case | 2 (`--quick`) + a sentinel re-measurement of the baseline |
| rate source | committed broker offsets on `block-trades` |
| CPU source | cgroup `cpu.stat usage_usec` |
| backlog | 280 000 000 records, 8 partitions, **5 outputs per input** |
| harness | `prove-it-scales`, used verbatim; `lib.py` sha256 `30afc9a454997263`, last modified 17:44 — before this session, and unchanged throughout |

**Scope, once:** this is one pipeline on one laptop. It supports *"this block-trade
allocation and position pipeline scaled this way on this rig"*, not *"Flink scales"*.

## The claim, and whether it was met

The claim written before building: *"doubling the worker's cores and its parallelism
doubles the trades it drains per second."*

| step | ratio | of linear | interval (95%) | adjacent pairs | met the claim? |
|---|---:|---:|---|---|---|
| **2 → 4 cores** | **1.764×** | **88.2%** | **1.683 – 1.846** | 1.723, 1.806 | **NO** — the whole interval is below the 1.90 floor |
| 1 → 2 cores | 2.346× | 117.3% | 2.246 – 2.263 | 2.250, 2.259 | yes on the arithmetic, but see below |

The claim is judged on the **lower bound** of the interval, not the point: a ratio that
*might* be linear has not been shown to be.

**Lead with 2 → 4.** It is the step someone actually buys, it has no privileged case in it,
and it misses.

**Do not believe the 1 → 2 figure.** 2.35× is superlinear, which the skill's own tiny-proof
bound calls a defect report, and the reason is visible in the table: the 1-core case is the
one that moved. Its two suite passes read 234 427 and 224 970 rec/s and the sentinel — the
same case re-measured at the very end — read 202 760, a **−14.5% drift across the suite**.
That drift is counted in the 1-core spread (14.3%, under the 20% ceiling, so the case stays
reportable) and it inflates every ratio the 1-core case is part of. The skill says not to run
the one-unit case at all when the claim is a step from two units up; the task asked for 1, 2
and 4, so it was run, and this is exactly the weakness the skill predicts.

## Completeness — proved separately, with no tolerances

12 000 000 block trades drained twice at the baseline, on build `ffc01f5c36588ad1`:
once cleanly (81.0 s), once with the task manager **killed mid-drain at 4 915 375 of
12 000 000 committed — 41% of the drain** (the kill lands on the first committed offset past
the configured 35%, because offsets commit once per checkpoint), which took 133.9 s including
the restart. Both arms printed the same answer:

```
12,000,000 trades | 64 symbol keys, 512 account keys | net qty 18,293,384 | notional 1,020,162,812,036
COMPLETENESS OK — every assertion held exactly, no tolerances
```

Asserted, with equality and no tolerance, against the generator's manifest (never against
anything the pipeline produced):

1. distinct symbols = 64 and distinct accounts = 512 — the cardinality predicted before building;
2. every per-key net quantity, notional and update count equals the manifest;
3. **the two paths agree exactly** — summed over 64 symbol positions and over 512 account
   positions, net quantity and notional are equal, because the allocation is integer
   largest-remainder and sums to the block quantity exactly;
4. update counts: one per trade by symbol, four per trade by account;
5. every key appears in exactly one output partition, so "last value per key" is well defined.

That is what makes the at-least-once sink safe: the emitted record is the **absolute**
position, so a replayed emission overwrites instead of adding, while the sums themselves are
keyed state under exactly-once checkpointing.

## The one thing I changed, and what I can and cannot claim about it

The 4-core case failed the cap-ownership guard twice at 92.7% and 92.9%, while the identical
build on a fresh topic read 96.3% — so the number wandered across a band straddling the
floor. Rather than invent a mechanism, I made one change and measured both arms:

| build | sink payload | 4-core rate | % of 4-core cap |
|---|---|---:|---:|
| `5793551a234b0cf6` | JSON, ~110 B (`{"kind":…,"key":…,"netQty":…}`) | 788 614 rec/s | 92.7%, 92.9% — refused |
| `ffc01f5c36588ad1` | compact, ~30 B (`key\|netQty\|netNotional\|updates`) | 920 060 rec/s | 98.8% — passes |

At four cores this pipeline writes 4.57M sink records/s; the JSON payload put roughly
390 MB/s onto a broker capped at 2.5 cores, the compact one about a third of that.
**That is an A/B on one rig with one variable — the build — and it is honest as far as it
goes, but it is two builds, not one, and the 4-core figure of the old build was itself
unstable (92.7 / 92.9 / 96.3). I am not claiming the payload size *caused* the recovery.
What I claim is narrower: with the compact payload the worker held its cap at every case, so
the table below is about cores.**

## What I did not explain

- **Why 2 → 4 returns 88% and not 95%.** I do not know. Per-core throughput falls 258 912 →
  228 328 rec/s (−11.8%) while the worker still holds 96.0% of its cap, the broker sits at
  0.61 of 2.5 cores, the source idles 1.9%, and GC *falls* from 6.1% to 2.8%. So it is not
  the broker, not a starved source, not GC, and not memory pressure — those are ruled out by
  measurement. What remains is unmeasured.
- **Context that bounds it:** the harness's own probe, run in the same image under the same
  caps, says this host does **2 → 4 = 98% register-only and 77% memory-bound**. The
  pipeline's 88% sits *between* those two bounds. A pipeline cannot beat its machine, and
  a memory-touching one on this laptop cannot reach 95% at 2 → 4. That is a bound, not a
  mechanism, and I did not measure which of the two arms this pipeline resembles.
- **Why the 1-core case drifted −14.5% across 27 minutes** while the 4-core case held to
  0.2%. Its GC is 15.5% of capacity against 2.8% at four cores — the 1-core worker gets
  1792 MB of process size against 4096 MB — so heap pressure is a *candidate*, but I ran no
  controlled comparison and will not assert it.
- **Where it stops.** Not located. `prove.py ceiling` (hold the worker at its largest case
  and starve the broker in steps) was not run. What the table does show is that the broker
  was nowhere near its limit at four cores, so the ceiling is further out than this table
  reaches.

## Deviations from the skill, stated plainly

1. **`prove.py all` could not be used.** Its preflight step raised `NameError: name 'out' is
   not defined` for any pipeline, and `all` stops at the first failing step. I ran the
   harness's own commands one at a time — the mode its README documents — chained in a single
   shell so there were no human gaps, with my own timestamped phase log
   (`results/phases-manual.log`). No harness file was copied, edited or re-implemented.
2. **`prove.py` changed on disk at 20:56:21, during the accepted chain.** The preflight bug
   is now fixed and a new undefined-name check appears in `replay`. `lib.py` — every
   threshold, guard, `run_case` and `build_table`, i.e. everything that produces a number —
   was last modified at 17:44, before this session, and did not change. The suite phases ran
   under the newer `prove.py`. I did not make either change.
3. **Completeness was skipped in chain 2b** because it had already passed for that identical
   build hash in the same stack session; the harness re-checks that gate itself before the
   suite. It was re-run in full for the final build.
4. **The 1-core case was run** although the skill advises against it when the claim is a step
   from two units up. The task asked for 1, 2 and 4.
5. **No dashboard was built.** The skill's §7 dashboard explains; it does not measure, and
   nothing in the table depends on it.
