> **QUICK LOOK — not a result.** One pass per case. No spread, so no table:
> these numbers say the rig ran clean and roughly how fast, and nothing about
> how repeatable the ratio is. The harness's own record shows single passes of
> recorded suites reading 2.04–2.27× where the full suite reported 2.15×, and
> 1.84–1.86× where it reported 1.85× — a band wider than the accept line.

## What was built

A Flink **DataStream** job — hand-written operators, no SQL and no Table API —
consuming block trades from Kafka and maintaining two books of running
positions:

```
Source: kafka-source -> allocate        one block trade becomes four updates:
                                        one for its symbol, one per allocation leg
        |  HASH (keyed by position key)
position -> positions: Writer/Committer keyed running position, absolute value
                                        per key, routed to its own topic
```

- **In:** `block-trades` — a JSON block trade (symbol, side, quantity, price,
  three accounts and their whole-percent weights), 8 partitions, ~136 bytes
  raw, 61 bytes on the broker after lz4.
- **Out:** `positions-by-symbol` and `positions-by-account`, one record per
  update carrying the **absolute** net position and update count for that key.
- **Fan-out: 4 outputs per input** (1 symbol + 3 allocation legs). The write
  side is four times the read side.
- **Cardinality, declared before it was measured: 1024 symbols, 3072 accounts.**
  Chosen so each key on either book takes the same update rate (N/1024), which
  keeps the keyed load even across subtasks rather than leaving it to the hash.
- Two vertices and one HASH edge **at every parallelism** — read back off the
  running plan on every case and compared. The baseline is not a chained
  special case.

## What was proven separately from speed

**Completeness passed for this exact build, with no tolerances**, on a
12,000,000-record backlog drained to the last record, twice:

| arm | drain | result |
|---|---|---|
| clean | 95.1 s | 1024 symbol keys, 3072 account keys, both books net 33,057,400, 12,000,000 symbol updates, 36,000,000 account updates — every one exactly the generator's manifest |
| **worker killed at 35%** (killed with 5,153,789 records committed; job back RUNNING on a replacement worker in 43 s) | 142.1 s | identical, exactly |

The killed arm wrote **12,063,864** records to `positions-by-symbol` where the
clean arm wrote 12,000,000 — 63,864 replayed duplicates — and the final position
for every one of the 4096 keys was still exactly right. That is the guarantee
pair doing its job: exactly-once state so a replayed record is not folded into
the snapshot twice, an at-least-once sink whose duplicates are harmless because
the value written is the absolute position, not a delta.

The expected answer came from the **input**: the generator writes a manifest of
per-key totals from `(seed, index)` alone. Two manifests from one seed are
byte-identical (`sha256 842246edaa9e…`), which the preflight checked.

## What was refused, and why

**The suite itself refused nothing** (`suite.json` → `"refusals": []`). Every
case cleared every live guard. Three refusals happened around it:

1. **Calibration tiny proof, 4-core case — REFUSED (case):**
   *"backlog drained (24,000,000 records) before the window closed — size it for
   warm-up + window at the largest case's rate."*
   My sizing error, not the rig's. I had guessed the per-record cost instead of
   measuring it. The refusal handed me the measurement I actually needed: the
   1-core case in the same run read 181,903 rec/s at 99.5% of cap with a 61.4 s
   warm-up, so a case needs ≈ rate × (warm-up + window + headroom) records. I
   re-sized `tinyCount` 24M → 104M and `backlog` 240M → 264M **from those two
   measured numbers**, changed nothing else, and ran the whole chain from cold.
   With the new sizes the 4-core tiny case read 583,079 rec/s and the 1→4 tiny
   ratio was 3.189×, inside the 3.00–5.00 bound.

2. **The guard self-test — 32 of 32 guards fired as expected** (`selftest.json`),
   each broken on purpose through the same code path the suite uses: a cap that
   did not apply, a busy cluster, a truncated backlog, a dead sampler, no job
   running, a window with too few commit boundaries, disagreeing vantage points,
   a case at 94% of cap, a noisy warm-up, a drifted sentinel, a host-side
   watcher, a disk that would not fit, and the `--quick` flag leaking into the
   record or the guards.

3. **The watcher reaper killed my own wait shell** (exit 144) during that
   self-test, because its command line named the project directory. That is the
   documented rule firing correctly on me; the run was unaffected. I moved the
   wait into a script whose command line names neither the project nor
   `prove.py`, and which sits outside the project directory.

## What I did not explain

**The 2→4 step came in at 1.35×, 68% of linear, and I do not know the cause.**

What the measurements rule out, each with the evidence:

- **Not the broker.** It used **0.25 of its 3-core cap (8%)** at the 4-core case,
  0.13 at 2 cores, 0.06 at 1. It was not CPU-bound at any case.
- **Not a starved source.** Source idle was **2.6%** against a 20% ceiling, and a
  starved input shows as idle rising with back-pressure at zero — back-pressure
  was 26.8% (internal, inside a capped worker, expected and gated on nothing).
- **Not the measurement.** Two independent vantage points — committed source
  offsets and sink growth divided by the fan-out — agreed to **0.04%**; the
  window held 7 commit boundaries over 70 s; 326 s of backlog remained at close.
- **Not the job graph.** Identical vertex count and edge ship strategies read off
  the running plan on every case, baseline included.
- **Not rig drift.** The sentinel re-measured the baseline at the end of the
  suite: +2.3%.

The one thing visible and unexplained: **at 4 cores the worker used 95.9% of its
cap and was throttled in 87% of cgroup periods, against 100% at 1 and 2 cores.**
The cap stopped being the only thing binding, and I did not measure what took
its place. Memory bandwidth, an 8-core Docker VM hosting a 4-core worker plus a
3-core broker plus a 0.5-core job manager, GC (26.3 s of GC in the 4-core
window against 5.8 s at 1 core, on 4× the capacity), shuffle cost at
parallelism 4, key skew across 4 subtasks — every one of those is a hypothesis.
None was tested with one rig, one build, one variable changed, both arms
measured, so none is offered here as a cause.

Three further things I am not explaining:

- **The broker used 0.06–0.25 cores while accepting 0.75–2.16M output records/s.**
  That is lower than I expected and I did not measure where the work went.
- **The tiny proof read the 4-core case at 583,079 rec/s; the suite read 539,902.**
  Different backlog (104M vs 264M), different warm-up and window settings — not
  a controlled comparison, so it is an observation and not evidence of anything.
- **1→2 came out at 2.11×, slightly superlinear.** With one pass per case there
  is no spread to say whether that is real.

**Where it stops: not located.** The `ceiling` command was not run — it is not
part of `all`, and the task asked for the fast look. All that can be said is
that the broker was nowhere near its cap at any case measured, so the ceiling
is not the broker's CPU at these sizes.
