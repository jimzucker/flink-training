## Where the four and a half hours went

The agent's own breakdown; it sums to 4 h 37 m against the 4 h 32 m between
its first and last tool call.

| phase | minutes |
|---|---:|
| design and build | 14 |
| the agent's own diagnosis of its first build | **172** |
| `prove.py all` (preflight 0.7 · completeness 9.3 · tiny proof 8.5 · fill 5.2 · suite 40.7) | 64 |
| ceiling (optional) | 14 |
| teardown and report | 13 |

The harness took 64 minutes to do everything it was asked. The first build
read 90–96% of its 4-core cap against the 95% floor, and the agent spent
2 h 52 m finding out why: four hypotheses tested and wrong (host contention,
unaligned checkpoints, checkpoint interval, sink batch size), then three
changes at once — key space raised from 64 symbols / 128 accounts to 512 /
4,096 after thread dumps showed the four `symbol-position` subtasks using
23.6 / 34.0 / 42.8 / 51.5 s of CPU over the same window; source prefetch
queue 2 → 8; a 22-field message with zstd sinks in place of an 8-field stub
with lz4. The 4-core case then read 100.1%. Because the three changes went in
together, which of them did it is not attributable, and the agent says so.

Run 11 lost its time to a rebuild for disk; this run lost more to a rebuild
for the cap floor. Both were the agent's pipeline, not the harness, and in
both the harness's verdict was right. Three of the last three runs on this
harness have had a first build or first pass sit at 90–97% of a cap floor —
run 11's 2c p1 at 96.4%, the plan's own rig at 95.6–96.8% at 4 cores, this
run's first build at 90–96% and its 1-core passes at 95.9% and 97.4%. That
is a pattern in the record, not an explanation.
