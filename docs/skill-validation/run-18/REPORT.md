# Block-trade allocation and running positions — a quick look at 1, 2 and 4 cores

**This is a quick look, not a result.** It was run with `prove.py all --quick`, which
measures each case **once** instead of three times. The harness stamps the table it
produced `quickLook: true`, `publishable: false`, and says so itself:

> **QUICK LOOK — not a result.** one pass per case. No spread, so no table: these numbers
> say the rig ran clean and roughly how fast, and nothing about how repeatable the ratio
> is. The record's own passes read 2.04-2.27x where a suite reported 2.15x. Do not publish
> or quote.

With that stated: the rig ran clean — every per-case guard stayed live and none of them
refused a case — and the two step ratios it read were

| step | ratio | of linear | passes |
|---|---:|---:|---:|
| **1 -> 2 cores** | **2.15x** | 107% | 1 (baseline case measured twice: p1 + sentinel) |
| **2 -> 4 cores** | **1.54x** | 77% | 1 |

Neither number is a proven ratio. A single pass lands anywhere in a band wider than the
difference between these two numbers, so the gap between them is not established either.

## The pipeline

One block trade in; two running positions out, both as absolute values.

```
kafka-source (parse)  ->  symbol-delta   -> keyBy(symbol)  -> symbol-position  -> positions-by-symbol
                      ->  account-delta  -> keyBy(account) -> account-position -> positions-by-account
```

The allocation is the fan-out: each block trade is booked against one symbol and split
across **4 client accounts**, so one input becomes **5** output records. 128 symbols and
1,024 accounts; both aggregations are hand-written `KeyedProcessFunction`s over
`ValueState<Long>`. Emitting the *absolute* position per key is what makes the sink
idempotent (at-least-once, no transactions); the state it is computed from is
checkpointed exactly-once, so a replayed record after a failure is not folded in twice.

The graph is three vertices and two hash edges at **every** parallelism, baseline
included — `keyBy` shuffles at parallelism 1 as well, so no case gets a chained-away
serialization that the others pay for. The harness read the shape off the running plan and
would have refused any row whose shape differed.

## What was refused, and why

| what | when | why |
|---|---|---|
| the 4-core tiny-proof case | first `all --quick`, 17:43 | `backlog headroom at close is 0 records (0.0s) < one checkpoint interval at the measured rate` — the 80M-record tiny backlog **drained under the job** mid-window. A sizing error of mine: I sized the backlogs from a guess of ~500k rec/s at 4 cores, and the pipeline runs at ~930k. The tiny proof failed, so the chain stopped before the fill — which is where that guard is meant to stop it. Fixed by `tinyCount` 80M -> 140M and `backlog.count` 200M -> 300M; nothing else changed, and the jar was not rebuilt (same build hash on both runs). |
| 34 guards, on purpose | tiny proof, second run | The live guard self-test broke every guard deliberately — wrong cap, busy cluster, truncated backlog against its manifest, a monitor dead at startup, no job running, host-side watchers, spread past the ceiling, a case measured only once, the quick flag leaking into the record or the guards, sentinel drift, the broker starved of page cache, a noisy warm-up ramp, the disk projection, the chain stopping at its first failing step. 34/34 fired as expected. |
| nothing in the suite | — | All four measured cases passed every per-case guard: worker >= 95% of cap, source idle below the 20% ceiling, >= 6 commit boundaries in the window, two vantage points within 0.4% (tolerance 5%), broker memory-limit hits **0**, backlog headroom 192–1010 s at close. |

Completeness passed for this build before any throughput was reported, with no tolerances:
8M trades drained twice — once clean, once with the task manager `docker kill`ed at 35% of
the drain — and both times all 128 symbol keys, all 1,024 account keys, every per-key
total and both aggregation paths matched the generator's manifest exactly
(`sum(symbols) = sum(accounts) = manifest = 111,556,900`). The killed arm wrote 8,024,858
symbol records for 8,000,000 trades — the replayed records the at-least-once sink is
allowed to produce — and still landed on the exact totals, which is the guarantee doing
what it was configured to do.

## What I did not explain

**2->4 came out at 1.54x where 1->2 came out at 2.15x, and I do not know why.** No
controlled comparison was run, so there is no mechanism here — only what was measured:

- at 4 cores the worker held **96.0% of its cap** (the harness's floor is 95%), so by the
  harness's own rule the component under test was still the constrained one;
- the broker used **0.52 of its 2.5 cores** and hit its container memory limit **zero**
  times inside the window, with 4 GiB of container memory;
- the source **idled 5.5%** of the window (ceiling 20%) — it was not waiting on input;
- internal back-pressure at the source fell from 53.0% (1 core) to 31.9% (4 cores);
- the job graph was identical across cases, and 8 partitions divide evenly by 1, 2 and 4
  (2 partitions per subtask at 4 cores).

Nothing in that list is a cause, and nothing on it is ruled out. Settling it needs one rig,
one build, one variable changed, both arms measured — which this quick look is not.

**1->2 at 107% of linear is also unexplained.** Above-linear on a single pass is exactly
what a one-pass table cannot distinguish from noise; the sentinel says the 1-core case
alone moved 7.5% within one suite.

**Where it stops is not measured.** `prove.py ceiling` was not run (it is not part of the
`all` chain), so the broker's 0.52-of-2.5 cores says only that the broker was not near its
own CPU cap in these four windows — it does not locate the ceiling.

**Scope.** This is one pipeline, one build, one laptop, one backlog. It supports statements
about *this* pipeline's throughput on this rig, and nothing about Flink or Kafka in general.

## The interview I could not hold

No human was available. These are the questions the skill says to ask one at a time, and
the assumption taken in place of each answer. Every one of them is a place where the study
could be aimed at the wrong thing.

| # | question | assumption taken |
|---|---|---|
| 1 | What is the input event, and what comes out? | A block trade in; a running net position per symbol and per account out, both as absolute values on Kafka. |
| 2 | Does one input become several outputs? | 4 client accounts per block trade -> 5 output records per input. |
| 3 | What are the keys, and how many distinct ones? | 128 symbols, 1,024 accounts — asserted exactly by the completeness verifier, not tolerated. |
| 4 | What has to be exactly right? | Running sums, so a replayed record is a wrong number: exactly-once checkpointing for the state, at-least-once for the sink, made safe by emitting the absolute position per key. Tested by killing a worker mid-drain. |
| 5 | Who watches the demo, and what must they believe? | Not knowable; built as a capacity number gated on correctness, which serves both audiences and privileges neither. |
| 6 | Where does it run? | Given: this laptop, everything in Docker. |
| 7 | What claim do you want to make? | Taken as: *"the throughput of this pipeline grows with the cores given to one worker."* This quick look does not prove it. |
| 8 | Which axis? | Given by the task (1, 2, 4 cores on one worker): one worker growing, parallelism = CPU cap = slots on every case. |
| 9 | Which API level? | Given: DataStream API, hand-written operators, no SQL and no Table API. |

One deliberate departure from the skill: section 5 says that if the claim is a step from
two units up, the one-unit case should not be run at all, because it is the structurally
weakest and noisiest case. The task asked for the 1->2 step, so the 1-core case was run —
and it is the only case whose two measurements disagree (7.5%).
