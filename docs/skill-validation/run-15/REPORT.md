# Block-trade allocation and running positions — a quick look at 1, 2 and 4 cores

**This is a smoke run, not a result.** Every case was measured **once**
(`prove.py all --quick`), and the harness stamps the table it produced
`quickLook: true`, `publishable: false`. In its own words:

> **QUICK LOOK — not a result.** one pass per case. No spread, so no table:
> these numbers say the rig ran clean and roughly how fast, and nothing about
> how repeatable the ratio is. The record's own passes read 2.04-2.27x where a
> suite reported 2.15x. Do not publish or quote.

The two step ratios below are therefore **single measurements**, not proven
ratios. The harness's own replay says a single pass of a recorded suite lands
anywhere in a band wider than the accept line, so neither number should be
quoted as what this pipeline does.

## What was built

Flink DataStream API, hand-written operators. Three vertices, two HASH edges,
**the same shape at parallelism 1, 2 and 4** — the harness reads it off the
running plan every case and refuses a row whose shape differs, so the baseline
is not a chained special case:

```
Source: kafka-source -> allocate          (one vertex)
   |- main output  --HASH by symbol-->        position-by-symbol  -> sink-by-symbol
   \- side output --HASH by (acct,symbol)-->  position-by-account -> sink-by-account
```

`allocate` parses a block trade and splits it across its four accounts
pro-rata on basis points, remainder to the last leg, so the legs sum to the
block quantity exactly. Each input produces exactly **5** outputs (1 symbol +
4 account). 32 symbols → 32 symbol keys; 128 accounts → 4,096 account-symbol
keys.

Guarantee, as two settings: **exactly-once checkpointing** for the running
sums, **at-least-once sink** made idempotent by emitting the absolute position
per key.

## Completeness — passed before any throughput was reported

16,000,000 trades drained to the last record, twice, at the baseline case, and
verified against a manifest derived from the **input** (it replays the
allocation rule over the trade ids; it never reads the pipeline). **No
tolerances.** Both arms:

* distinct symbol keys = 32 (= predicted), distinct account-symbol keys = 4,096 (= predicted)
* every symbol position and every account position equal to the manifest, quantity **and** update count
* the two paths agree exactly: per symbol, the account positions sum to the symbol position and their update counts to 4 × trades
* totals: net −6,568,415 by symbol == −6,568,415 by account, 16,000,000 symbol updates, 64,000,000 allocation updates

The second arm killed the task manager mid-drain at 5,799,124 records
committed; the job restarted on a replacement worker and **every assertion
above still held exactly**, including the per-key update counts. That is the
test that the guarantee configured is the guarantee we have.

Tiny proof, before the fill: 1 → 4 = **4.11×** (bounds 3.00–5.00), both cases
at 99.4–99.7% of cap. Guard self-test: **34 guards broken on purpose, 34
refused.**

## What was refused, and why

| refusal | where | what it was, and what I did |
|---|---|---|
| **`backlog headroom at close is 6,709,849 records (6.9 s) < one checkpoint interval at the measured rate`** | tiny proof, 4-core case, attempt 2 | A sizing error of mine. I had sized the backlogs for ~450k rec/s; the 4-core case actually runs at ~970k, so an 80M tiny backlog was ~2M records short. Raised the tiny backlog to 160M and the suite backlog from 320M to 400M, and re-ran the chain. |
| **`task manager used 95.0% of its 1-core cap (floor 95%)`** and **`94.7% of its 2-core cap`** | suite, attempt 3, first try | Two cases landed a fraction under the cap floor. **Retried the suite once, unchanged** — which is what the harness sanctions for a plainly transient case refusal — and all three cases passed at 97.7–100.4%. The refused run's own sentinel is the reason I judged it transient: the *same* 1-core case, later in the same suite, read 99.5% with nothing changed. |
| 34 guards in the self-test | tiny proof | All fired on purpose. Included the reaper: it found and killed the shell I had left waiting on `results/DONE`, twice. That is the guard working, and it is why the skill says to start no host-side watcher. |
| Docker Desktop memory | before the run | Not a harness refusal — this environment blocked raising the VM's memory from 7.65 GiB, so the stack had to fit as it is. See below. |

Nothing was refused in the run that produced the table above, and nothing was
carried over from a run that failed: the table is one build, one fill, one
suite.

## What I did not explain

**Why two cases read 94.7% and 95.0% of cap on the first suite attempt, and
97.7–100.4% on the second, with nothing changed. I do not know.** What I can
rule out, with the numbers from the refused cases themselves:

* **Not the broker.** It sat at 0.12–0.60 of its 2.5-core cap (5–24%) and hit its container memory limit **zero** times inside every window.
* **Not a starved source.** Source idle was 0.5–4.5%; a starved input shows as busy falling with back-pressure at zero, and back-pressure was 43–63% — internal, inside a capped worker, which is expected and gated on nothing.
* **Not the cap failing to apply.** Throttled periods were 100% in all three refused cases: the cap was binding.

A plausible story is available — the first case of a suite runs immediately
after a 26 GB fill, on a broker whose page cache is full of what it just wrote
— but that is a hypothesis, not a measurement. Separating it from run-to-run
noise needs a controlled comparison I did not run, and one pass per case cannot
distinguish an order effect from noise at all. That is the same reason this
table is not publishable.

**Where it stops is also unmeasured.** `prove.py ceiling` was not run. The
broker was at 26% of its cap at the largest case and the 2→4 step is already
92% of linear, so the ceiling is somewhere above 4 cores and I cannot say
where. The host has 8 cores and the stack already reserves 7 of them.

**One deviation from the harness's own measured configuration**, stated because
it is a difference and I did not test it: `harness/README.md` prescribes a
4 GiB broker with a 3 G heap, measured against a 2 GiB arm that thrashed. This
Docker VM has 7.65 GiB and raising it was blocked, so the broker ran with a
5 GiB limit and a **1 G** heap — small heap, limit far above anything it
reaches, leaving ~2 GB of page cache, which is what the README's clean arm
measured. The broker-memory guard was live in every case and never fired. I did
not run the 4 GiB / 3 G arm here, so this is reasoning from their measurement,
not from mine.
