#### Review packet — Step 09: Latency

##### Two numbers, because one would flatter the result

**What the pipeline takes** — operator histogram, on the dashboard:
```
p50   59 ms      p99  110 ms
```

**What a consumer actually waits for** — measured from *outside*, because an operator can't see it:
```
orders                 p50=9      p99=17     max=22      (ms)
positions-by-symbol    p50=2488   p99=4981   max=4988    (ms)
positions-by-account   p50=2524   p99=4985   max=5024    (ms)
```

The input path is single-digit milliseconds. **The positions are not** — and the difference is the exactly-once commit, not the work. Reporting the 59ms alone would have looked excellent while a consumer waited two and a half seconds.

##### Proved by changing one setting

| Checkpoint interval | p50 | max |
|---|---|---|
| 5s | 2488 ms | 4988 ms |
| **1s** | **497 ms** | **1041 ms** |

Five times shorter interval, five times lower latency, **max landing inside one interval each time** — precisely what a uniform wait for the next commit looks like. That's the strongest available evidence the delay is the *guarantee*, not the pipeline.

All of it is measurable only because the generator stamps wall-clock times — the step-02 decision paying off.
