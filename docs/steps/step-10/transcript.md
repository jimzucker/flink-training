| Target | Interval | What `Thread.sleep` actually did | Achieved |

target 20000   achieved 22680/sec

**Response**

Both good questions, and the first one exposes an overclaim on my part.

##### Determinism with multiple threads — we *can*, I was wrong to say otherwise

What actually breaks under naive threading is two things, and both are fixable:

1. **Shared RNG.** Threads pulling from one `Random` get values in nondeterministic order. Fix: derive a per-thread seed from `(seed, threadIndex)` and have thread *i* generate records *i, i+N, i+2N…*. Record content then depends only on its sequence number, not on timing.

2. **Interleaved writes to the same partition.** This is the real one. Byte-identical topics require each partition's record sequence to be fixed. Orders are keyed by `tradeId`, which hashes across partitions — so two threads both produce records landing in partition 2, and who gets there first varies per run. Different offsets, different bytes.

The fix is **one writer per partition**: assign thread *t* a disjoint set of partitions and give the `ProducerRecord` an explicit partition rather than letting the key hash decide. Each partition then has exactly one writer emitting in sequence order, and replay is byte-identical again.

Two constraints on that:
- **Threads must divide partitions evenly** — 4 partitions means 1, 2 or 4 threads.
- **Prices must stay as they are.** They're keyed by symbol, and the pipeline depends on per-symbol ordering — that's exactly the tie-break that bit us on price-at-close. Prices only run at 1000/sec, so there's no reason to touch them. Parallelise the trade producer only.

So it's a design constraint, not an impossibility. I should have said that rather than "it would break determinism".

##### "Stop requests queueing"

The broker has two thread pools:

- **network threads** (`num.network.threads`, default 3) read bytes off sockets and place complete requests onto a shared queue
- **io / request-handler threads** (`num.io.threads`, default 8) pull from that queue and do the work — append to the log, wait for acks, send the response

`queued.max.requests` (default 500) is that queue's depth. When all 8 handlers are busy, an arriving produce request **sits in the queue doing nothing** until a handler frees up. That wait is pure latency — the request isn't being processed, it's waiting for a worker.

Going to 16 handlers means fewer requests wait their turn. Throughput doesn't move, because what limits it is disk and page-cache bandwidth — the same bytes get written either way. But each request spends far less time waiting, which is the p95 136 ms → 14 ms.

Supermarket checkout: opening more lanes doesn't sell more groceries per hour if the loading dock is the limit, but it cuts how long each customer stands in line.

That's exactly what the **"Broker — produce request time"** panel splits out: `local` time is the handler actually working, `queued` time is the request waiting for one. If queued time climbs while local stays flat, add handlers; if local climbs, you're out of real capacity.
