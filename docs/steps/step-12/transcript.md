**Response**

**Capping the cores.**

In step 10 we varied parallelism alone while the TaskManager had all 8 cores. Flink already had every core it could use, so more parallelism just spread the same work across more threads — and the broker was the ceiling regardless. The result was flat:

```
  step 10, parallelism 1 / 2 / 4, cores unlimited:
     137,931  /  142,857  /  131,147     ← flat
```

In step 12 cores and parallelism move **together** — one unit is one core *plus* one degree of parallelism. That makes Flink the constraint at the bottom of the curve, so adding capacity actually produces throughput:

```
  step 12, 1 / 2 / 4 / 8 units:
      30,505  /   65,721  /  129,056  /  151,969     ← 2.15x, 1.96x, 1.18x
```

The principle underneath: **you can only demonstrate that something scales when it is the thing that's constrained.** Step 10 spent a lot of effort trying to make Flink the bottleneck by scaling the load up — 88M records, then 32 vCPUs and three brokers on AWS. Shrinking Flink gets there in one line of compose config.

There's a second half to the answer, though, and it's less flattering: **we tried this in step 10 and it appeared not to work.** The harness set `TASKMANAGER_CPUS` as a prefix on one `docker compose` command, and the `run --rm submit` that followed couldn't see the variable — so compose computed a different desired config and silently recreated the container *unlimited*, right before each measurement. Those runs reported "1 core sustains 148,148 orders/sec", which was really "unlimited cores". The idea was right and the evidence was fabricated by the tooling.

So the fix is two things, and the second is the one that cost the time:

1. **Scale cores with parallelism** — the design.
2. **`export` the variable, and refuse to report unless `NanoCpus` on the container matches what was asked** — so the design is actually in effect when the number is taken.

The supporting changes that make the number trustworthy rather than merely favourable: partitions held constant at 8 across all cases, a 240-second warmup to clear the cold start, and a backlog large enough that no case runs out of data mid-window. Each of those was a wrong answer at some point this week.

##### Ranked, cheapest first

**1. Give Kafka real storage.** A named volume avoids overlay2's copy-on-write; `tmpfs` removes disk entirely. One line of compose, and it's decisive: if the ceiling jumps, the constraint was the container filesystem, not Kafka. My bet is here.

**Response**

Let me be precise, since it matters for reading the table:

**Orders/sec.**

The script counts records arriving in `positions-by-symbol` over the window. Sink ③ emits **exactly one record per order** — the block trade taken whole, keyed by symbol — so that count *is* the order count.

| | at 8 units |
|---|---|

That last line is the one to compare against the ~750,000 broker ceiling — the broker doesn't care about orders, only records.

Two clarifications on "end to end", because the phrase could mislead:

**It's not the whole pipeline.** It measures Part 1's symbol branch. Part 2 (market value) is running concurrently and consuming from both position topics, so it's fully loading the system — but it isn't in the counted number. It couldn't be: sinks ⑤ and ⑥ emit once per key per window (4 and 16 records per window), which is a fixed trickle rather than anything proportional to throughput.

**It's throughput, not latency.** The window measures records per second, not how long a record takes to traverse the pipeline. End-to-end latency is a separate metric — `processingLatencyMillis`, creation time to sink — which is what the latency panels and step 09 report, and it's the one that blew up to 110 seconds under saturation.

So if someone asks "how fast is it?", the honest answer has both halves: **151,969 orders/sec sustained, and each order visible at the sink within roughly a checkpoint interval when not saturated.**
