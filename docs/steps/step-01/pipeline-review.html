Step 01 · design review

Block Trade Pipeline

Block trades in, positions and market value out — aggregated two ways in parallel. This is the design for review before any code is written.

What it does

A block trade is one order split across several accounts. A trade of 400 shares allocated to four accounts becomes four allocations of 100.

That split is the whole point of the exercise. The same stream is aggregated two different ways at the same time: by symbol, giving one key per symbol, and by account / sub-account / symbol, giving one key per account-and-symbol pair. Part 1 produces positions. Part 2 joins prices to those positions and produces market value.

How market value is computed

A tumbling one-minute window, taking the price at window close — not an average or a VWAP across the window.

marketValue = position quantity at window close
× last price for that symbol at or before window close

Both inputs are read as of the same instant, so the number is a snapshot that reconciles against the position topic at that timestamp. An averaged price would match nothing observable anywhere in the system, which makes it impossible to explain when someone asks where a figure came from.

Buys and sells

BUY increases the position, SELL decreases it. Position is a running signed sum, not a count, so a key whose sells exceed its buys holds a legitimate negative — a short position.

The generator emits a random mix of both, because a demo where everything is a buy proves nothing about sign handling. Random does not mean unverifiable: the generator is seeded, so the mix is identical on every run and the expected net position for each key is arithmetic that can be asserted exactly. Fixtures cover a key that nets positive, one that nets negative, and one that nets to zero.

Side affects values only. It changes the quantity on a key; it never changes how many keys exist or how often they update — so every rate and key count above holds regardless of the buy/sell mix.

Design decisions

Numbering follows the assignment

The requirements already name the outputs sinks 3 – 6, which fixes 1 and 2 as the sources. The diagram, the table above and the Grafana panel order all use the same six numbers, so a figure on a dashboard maps to the diagram without translation.

Two aggregations, one source

Both position aggregations are keyed off a single split of the order stream, running in parallel. Demonstrating that is the exercise.

One shared price stream

Prices are consumed once and used by both joins, keyed on symbol in both cases. For the account-keyed join the symbol is extracted from the composite key.

Event time, not processing time

Windows key off a timestamp stamped at the generator. A slow consumer changes latency but never changes results.

Every record carries tradeId

A single trade can be followed from orders through to both market value topics in the logs, so any number on screen traces back to its input.

Hand-drawn SVG

Kafka icons, numbered badges and key/value labels on every edge are all required. Mermaid renders none of them cleanly, and SVG scales into the final deck without redrawing.

Diagram rules

The assignment sets six rules for a pipeline diagram. Checked one at a time.

  • ✓Keys and values between operators — every edge labelled K: / V:, with the notation defined in the legend
  • ✓Sources and sinks shown — generators outlined green on the left, topic glyph on all six topics
  • ✓Colours used sparingly — three only: blue for Part 1, amber for Part 2 and the price stream, green for generators. Everything else greyscale
  • ✓Numbered left to right in talk order — sources first, then Part 1 sinks, then Part 2 sinks
  • ✓Kafka icons for Kafka — topic glyph on all six; generators are plain boxes because they are not Kafka
  • ✓Boxes name the operation — Split, Aggregate, Join, Window

The single line crossing — the price stream passing the positions-by-account feed — is drawn as a hop, so it reads as passing over rather than connecting to.

Settled in review

Prices arrive in order

The prices topic is keyed by symbol, so every price for a symbol lands on one partition and Kafka preserves order within it. A single seeded generator emits them in event-time order. Nothing can overtake anything, so the watermark uses monotonically-increasing timestamps and allowed lateness is zero.

Every key emits every minute

A key with no trade during a minute still holds a position, so it still emits. That is what makes sinks 5 and 6 a steady 4 and 16 per minute rather than a count that rises and falls with activity.

Every key starts flat

Positions open at zero. There is no opening book to load, so the state at any moment is derivable from the trades alone.

The one thing to watch

Not lateness — idleness. Each join has two inputs and its watermark advances at the slower of them. If an input goes quiet, the watermark stalls and the one-minute windows stop firing, even though every record that did arrive was perfectly in order. Sinks 5 and 6 go silent, which during a demo looks exactly like a broken pipeline.

The fix is an idle-source timeout: after a short period with no records, a partition stops holding the watermark back. That is configuration, not semantics — it changes when a window fires, never what it contains. Verified by running with fewer active symbols than partitions and confirming both sinks still emit on the minute.
