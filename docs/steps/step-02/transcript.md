#### Review packet — Step 02: Generators

##### What I built

Kafka in Docker with the six topics, a `common` module (domain + JSON), and a `generators` module publishing block trades and prices at the demo rates.

**The core design call:** the generators are *pure seeded iterators* — no clock, no Kafka inside them. Event time comes from a counter, so the sequence a seed produces is identical whether a test pulls it as fast as it can or a publisher paces it at 10/sec. That's what makes the demo randomized **and** exactly reproducible, and it means a slow consumer can never change the data. Pacing lives in a separate `Pacer` that computes each target from the run start, so a long run can't drift behind its nominal rate.

##### How it's verified

**19 tests, `mvn verify` green.**

| Suite | # | Protects |
|---|---|---|
| `BlockTradeGeneratorTest` | 7 | allocations sum to block; split covers every account; both sides produced; sign follows side; event time monotonic; ids unique + sorted |
| `ExpectedNumbersTest` | 4 | the assignment's table as assertions — 10/sec, 40 allocations, 4 and 16 keys |
| `DeterminismTest` | 6 | byte-identical across runs; different seed differs; sequence pinned by hash; prices exact quarters |
| `KafkaPublisherIT` | 2 | real-broker round-trip; **every symbol occupies exactly one partition** |

That last one matters most — it proves against a real broker the claim your review turned on: prices keyed by symbol can't be spread across partitions, so they can't be consumed out of order.

##### Decisions you may disagree with

1. **Testcontainers, as flagged.** The IT spins up its own broker, so a clean CI runner needs Docker but not a started stack. Unit tests need neither. Split via `*Test` (surefire) vs `*IT` (failsafe).
2. **Every allocation is 100, block is 400.** Deliberately different numbers — if the split were broken and each allocation carried the whole block, positions would be 4× too large and nothing else would catch it.
3. **gzip not lz4.** Native codecs make Java 17 print a restricted-method warning on every start. The assignment says demo live; a clean console beat the compression difference at these volumes.
4. **Price walks in quarters from round openings** (100/200/300/400). Exactly representable, checkable by eye.
5. **Prices seeded at `seed + 1`** so changing the price rate can't shift the trade sequence.
6. **A pinned SHA-256 of the demo sequence.** Catches accidental changes to generation order or JSON shape. It locks stability, not correctness — the invariant tests do correctness.

##### Questions

1. **Price tick rate defaults to 1/sec (4 prices/sec).** The assignment fixes trades at 10/sec but says nothing about prices. Is 1/sec the right demo default, or would you rather see prices move faster on the dashboard?
2. **Every block splits across all 4 accounts, always.** That's what yields exactly 40/sec and 16 keys. Should some trades allocate to fewer accounts — more realistic, but then the numbers stop being a clean 40 and 16.
3. **Sub-account is fixed at `SUB1`.** That's what makes it 4×4=16 rather than more. Confirm you want one sub-account per account.
4. **Seed 42 and a fixed start epoch (`1700000000000`).** Event times are therefore historical, not wall-clock. Fine for correctness; worth knowing before Grafana, since panels will show 2023 timestamps unless I switch to wall-clock event time for the demo.

**Question 4 is the one I'd most like an answer on** — it's cheap now and awkward after the dashboards exist.
