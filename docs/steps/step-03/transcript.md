##### How

The tolerance was never about measurement noise — it came from bounding a run by **time** while emission is **paced**. Fix the mismatch and the slop disappears:

| Slop | Cause | Fix |
|---|---|---|
| count 100 *or* 101 | stop falls between pacer ticks | bound by **record count** |
| one symbol a price ahead | run ends mid round-robin cycle | make price count a multiple of symbol count (400 = 4×100) |
| per-symbol counts look uneven | `--max-messages` slices across partitions | drain the whole topic |

`scripts/verify-run.sh` does the whole thing in one command: reset topics → emit exactly 100 trades and 400 prices in replay mode → assert. Two invocations produce byte-identical topics, down to the same `43 BUY / 57 SELL` mix.

##### A fourth cause, found while fixing the first three

The first attempt failed intermittently. **Kafka topic deletion is asynchronous** — recreating too quickly leaves the previous run's records in place, so the count check was reading stale data. That's *worse* than a tolerance: it fails for the wrong reason and would have been debugged as a generator bug. The script now waits for deletion to complete and aborts rather than verifying stale data.

##### One check the exactness bought

`missing tradeIds` verifies the full expected id set `T000000000`–`T000000099` is present. A count alone passes if a record is both dropped and duplicated; the id set doesn't. That check is only expressible because the expected set is exactly known — it can't exist alongside a tolerance.

The live demo path is unaffected: `java -jar generators/target/generators.jar` still runs unbounded on the wall clock. Exactness is for verification; the demo is for watching.
